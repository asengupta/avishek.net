Eliminating GOTOs

TL;DRMoving COBOL to Java, or any language without an unrestricted jump, means removing every GO TO first: a code generator that only emits if and while has nothing to work from otherwise. These rewrites are that clearing step.

Read first: nothing — standalone

A GO TO names where control goes next, not which statements it skips. When the jump and its label share a block, the skipped statements are the ones between them, and an IF can be wrapped around those. When the jump is nested inside an IF and the label is a paragraph further out, no one block holds "what the jump skips".

In the example below, GO TO SZ1 sits inside an IF inside paragraph SA1. The rewrite climbs it out one level at a time, leaving a flag behind, until the jump and SZ1 are siblings; a forward rewrite then removes it. The result has no GO TO and prints the same lines whatever WS-NUM1 holds.

Sections, paragraphs and fall-through are in the COBOL/CICS primer.

Why the jump cannot just be wrapped

In the original fragment, the line GO TO SZ1 says "control passes to SZ1", and nothing in the tree's shape shows that this means skipping SA1-1 and SA1-2. In the rewritten fragment the same fact is on the page: those two lines are inside IF NOT FLAG. The rewrite does not change what the program does, as the trace table shows; it changes whether a reader, or anything built on the tree's shape, can see it.

The forward rewrite alone could not do this, because it needs one block that directly holds the jump and the label. In the example's tree no scope does:

scopeholds GO TO SZ1holds SZ1holds SA1-1, SA1-2
THEN of the IFyesnono
SA1nonoyes
Snoyesno

Steps 1 and 2 of the walk move the jump down this table's rows: into SA1 after step 1, into S after step 2, where the last row then reads yes for both the jump and SZ1.

When the target is in an outer scope

Each climb is one move, applied at whatever depth the jump is: wrap everything after the jump, in the scope it is in, inside an IF guarded by NOT a flag; set that flag where the jump was; re-emit the jump one level up, reading the flag. Repeat until the jump and its label are siblings, then apply the forward or backward rewrite. This is Erosa and Hendren's outward-movement transformation.[1] In the walk, step 1's guard was empty, because nothing followed the jump in the THEN branch. Traced both ways: when something holds, the original runs I1 then jumps straight to LABEL; the rewrite runs I1, sets the flag, skips I2, and the re-emitted jump skips O2 — the same. When something does not hold, both run O2 then reach LABEL, and the flag, cleared on the way in, is false.

The SET FLAG TO FALSE in the second diagram is not optional. Inside a loop, a flag left TRUE by one pass makes the next pass skip O2 and take the jump again, though the jump never fired; the stale-flag table under what goes wrong shows it on the example. (Erosa and Hendren initialise the flag and clear it again at the label; clearing it just before the construct, as here and in step 1 of the walk, has the same effect for one climb. cobol-rekt does neither — a known gap.)

A forward jump becomes an IF

Step 3 of the walk was this rewrite with nothing to wrap. Here it is where the jump and its label already share a block and statements sit between them:

flowchart TD
    J["IF C1 GOTO SKIP"] -->|"not C1"| S1
    S1 --> S2
    S2 --> Skip["SKIP: S3"]
    J -->|C1| Skip

Read it the other way round: S1 and S2 run exactly when the jump is not taken — when C1 does not hold. That is an IF waiting to be written down.

A backward jump becomes a loop

The example has no backward jump. A conditional jump back to a label earlier in the same block looks like this:

flowchart TD
    Loop["LOOP: S1"] --> S2
    S2 --> Test["IF C1 GOTO LOOP"]
    Test -->|C1| Loop
    Test -->|"not C1"| S3

Read the other way round: S1 and S2 run again every time C1 holds, checked after they run — a loop whose test comes at the bottom, not the top.

Rewriting the backward jump (1 step)

  1. The label itself and everything up to, but not including, the jump are the loop's body — the jump statement contributes its condition, not its own place in the body.

Compare the two step-1 graphs: the forward rewrite's guard is NOT C1, this loop's test is C1 unchanged. The back-jump's condition already says "go again", which is exactly what a bottom-tested loop's condition means too.

The rules

classify: forward if the jump comes before its label in tree order, else backward
climb (jump in scope B, condition C):
  SET FLAG TO FALSE before the construct holding B
  SET FLAG TO C where the jump was
  IF NOT FLAG around the rest of B
  IF FLAG GO TO label right after the construct
repeat climb until jump and label are siblings
forward: IF NOT C around the statements strictly between jump and label
backward: loop tested after the body, condition C; body = label up to the jump

Each line was applied above. classify is the walk's first panel. climb is steps 1 and 2: step 1 shows the clear, the set (C is true: GO TO SZ1 is unconditional in its branch) and the re-emitted jump; step 2 shows the guard, and a set that vanishes because C is FLAG. forward is step 3, and step 1 of the forward walk. backward is step 1 of the backward walk.

Where this shows up in reverse engineering

  • The order these rules run in matters: classification comes first and comes purely from where the jump and its label sit in the statement tree, as in the walk's first panel. A cross-scope jump climbs outward first; only once it and its label are siblings does the forward or backward rewrite apply. For the example:
    classify: forwardclimb: step 1climb: step 2forward: step 3
  • Legacy-to-modern migration, directly: turning COBOL control flow into Java, or any other target that lacks an unrestricted jump, has to clear every GO TO out before a code generator can start. The example's walk is that clearing step for one jump; a program with many runs it once per jump.
  • Why local rules, not the universal construction: a COBOL GO TO can only target a paragraph, and paragraph labels sit at the top level of their section, never inside a nested IF or loop — SZ1 in the example's tree is a child of S. So a jump only ever needs to move outward, as in steps 1 and 2, never flattening the program into one dispatch loop — the structured program theorem's generic fallback.

What goes wrong

  • Climbing out is implemented; climbing in or sideways is not. A jump into a scope it is not currently in, or across to a sibling scope's interior, needs a different transformation. cobol-rekt's README states that the outward transformation is the only one in the paper applicable to COBOL, and that the other three are not implemented.
    label sitsjump must movein cobol-rekt
    further out (SZ1 in the example)outwardimplemented
    inside a nested blockinward or sidewaysnot implemented
    The second row cannot arise from a COBOL GO TO, whose label is always a paragraph; it arises in languages that can label a statement inside a block.
  • The fresh flag is not fresh at all. Each climb needs a flag, but cobol-rekt uses one hard-coded name for every climb of every jump, and another fixed name for the forward and backward rewrites. Its README acknowledges these names are not yet unique.

    After the walk, the tree that held GO TO SZ1 no longer has it. Tree zippers are related background: they show how one could make the same deep edits to an immutable tree, building a new path to a new root and leaving the original as it was. This pass does not. Where this is used

Clearing arbitrary jumps out of legacy procedural code one block at a time, as a step before translating it into a language that only has structured control flow. Best suited to jumps confined to a modest span of code, like one section: the example's jump climbed two levels and left one guard. A jump spanning most of a large program climbs through most of that program's nesting, adding a guard at each level, before it reaches a scope it shares with its label.
