Value sets and dynamic calls

TL;DRA call graph read straight off the source has holes wherever a program calls through a field — menus, routers, transaction dispatchers. This fills those edges in from the values the field can hold, and marks the ones it cannot, instead of leaving them out or guessing.

Read first: Fixpoints and worklists, Gen/kill and reaching definitions

VALSETS moves 'PROGB' into WS-PGM on one arm of an IF and 'PROGC' on the other, then does CALL WS-PGM; it also does CALL WS-OTHER, which nothing assigns. Value sets track every value a field may hold, and why that list may be short: the first call gets candidate edges to PROGB and PROGC, the second a visible unresolved node, reason uninitialised.

New to CALL, MOVE or PIC X(8)? The COBOL/CICS primer has the vocabulary.

Sets, and reasons they may be short

The walk carried, for every field, the set of byte values it may hold after each statement. Follow WS-PGM through it: a MOVE of a literal sets the set to exactly that value (rows 1 and 2, steps 2 and 3 of the walk); where the two arms of the IF meet, take the union (row 3, step 4); at a CALL through the field, the set is the list of programs that call could reach (row 4, also step 4). A MOVE from another field, which the example does not have, copies that field's set.

#statementWS-PGM's set after it
1MOVE 'PROGB' TO WS-PGM (then-arm){'PROGB␣␣␣'}
2MOVE 'PROGC' TO WS-PGM (else-arm){'PROGC␣␣␣'}
3END-IF (arms meet){'PROGB␣␣␣', 'PROGC␣␣␣'}
4CALL WS-PGMcan reach PROGB, PROGC

The set can be incomplete: the value may come from a file, from a caller, or from nowhere the analysis can see. So each set also carries reasons it may be missing values, and the answer table under the example shows both readings. WS-PGM ends with two values and no reasons: "these and no others". WS-OTHER is never assigned, so from step 1 to the call in step 5 it carries no values and the reason uninitialised: "at least these" — here, at least nothing.

Why a call through a field needs this

CALL 'PROGB'.   target in the source:
                edge to PROGB
CALL WS-PGM.    target is whatever
                WS-PGM holds

The first call names its target; a call graph can draw that edge by reading it. The second calls whatever is in WS-PGM when it runs, which in VALSETS is PROGB on one arm of the IF and PROGC on the other. Reading statements alone gives the example's edgeless read alone box; the walk fills in with value sets.

Where this shows up

  • A menu, a router, a transaction dispatcher — any program whose next call is chosen by a field's runtime value — looks like the edgeless read alone box until value sets turn it into with value sets: real edges, and a visible node where the answer is unknown.
  • On the Java side, a backward data-dependency walk across method boundaries can resolve a literal that reaches a dynamically-dispatched call's argument several call frames up: the same question, "what value could this hold", answered by walking data flow backward instead of forward.
  • Virtual dispatch resolution is the same kind of set one level up: every concrete class an interface call's receiver could be at runtime, with classes where the graph has PROGB and PROGC.

The rule

value set = (values, reasons)
entry:
  f := ({f's VALUE bytes}, {})
    if f has a VALUE clause,
    else ({}, {uninitialised})
MOVE literal TO f:
  f := ({literal padded or truncated
    to f}, {})
MOVE g TO f:
  f := g's set
merge:
  (values₁ ∪ values₂, reasons₁ ∪ reasons₂);
  if more than 32 values, keep the first
  32 in sorted order and add over-budget
call through f:
  candidates = trimmed values of f,
  reasons = f's reasons

A call site then becomes one of three things in the graph. The table after the list has one site of each kind: the two calls of VALSETS, and CALL WS-OTHER in the VALUE 'PROGD' variant above (call that variant VALSETV).

  • Proven — exactly one candidate and no reasons. An ordinary call edge, as if the name were written in the source: row 3, VALSETV → PROGD.
  • Candidates — any other site with at least one candidate. One edge per candidate, marked as possible rather than certain: row 1, the two dashed edges in the graph under the example.
  • Unresolved — no candidates. A single dynamic-target node carrying the expression and the reasons, so the hole is visible rather than silent: row 2, the VALSETS.WS-OTHER node in that graph.

Reasons taxonomy

Each reason explains why a value set may be incomplete — why the true set of values could be larger than what the analysis found.

uninitialised
Some path reaches this point without an exact write to the field, and no WORKING-STORAGE VALUE that cobble can image (text, figurative, or unsigned zoned) covers it. On that path its value is whatever the storage started as. (Introduced here.)

Example: row 2 of the three-way table above. Nothing writes WS-OTHER between step 1 of the walk and the call in step 5, so the call reads whatever the storage started as.

siteVALSETS: CALL WS-OTHER (walk step 5)
candidatesnone
reasonsuninitialised
over-budget
More than 32 values reached the field. The first 32 in sorted order are kept; the rest are dropped. The field may have that many possible values — some may come from paths that never actually run — but the analysis cannot carry all of them. (Introduced here.)

Example: an EVALUATE whose 33 arms each move a different name into WS-PGM. The arms' sets merge into 33 values, one over the budget: sorted, PROG01 to PROG32 are kept and PROG33 is dropped.

EVALUATE WS-CHOICE
    WHEN 1   MOVE 'PROG01' TO WS-PGM
    WHEN 2   MOVE 'PROG02' TO WS-PGM
      ...    (one arm each, PROG03 to PROG32)
    WHEN OTHER MOVE 'PROG33' TO WS-PGM
END-EVALUATE.
CALL WS-PGM.  candidates PROG01 … PROG32
              reasons    over-budget
incomplete-walk
The fixpoint stopped before settling because it ran out of its sweep budget — the cap on how many passes over the program it may make. Values that would have arrived on later passes are missing. See bounded sweeps.
hop-limit
The cross-program walk — following a field's bytes backwards from one program into the programs that handed them over (answering every walk once) — was cut after a fixed number of program crossings. Programs beyond that depth were never visited. See bounding walks by crossings.
readback-skipped
The cross-program walk was told not to follow bytes a called program writes back to its caller, so names a callee puts in the commarea are missing. See bounding walks by crossings.

The value comes from somewhere a single program's walk cannot follow. In the fragment, each call reads a field filled from one of these places; the reason on the right is what the fixpoint records for that call, and none of them gets a candidate.

inbound-linkage
The bytes are in LINKAGE: a caller handed them in. Also used when a cross-program walk goes round a cycle of programs and finds nothing. See local site resolution and answering every walk once.
from-callee
A LINK or CALL BY REFERENCE handed the field to another program, which may have written it. See local site resolution.
from-file
A READ or a CICS file command put the value there. See local site resolution.
not-a-literal
The value is not a quoted literal, so the analysis does not evaluate it: arithmetic (ADD through COMPUTE), STRING, INITIALIZE, a numeric or figurative MOVE such as MOVE 0 or MOVE SPACES, a non-file CICS receiver such as RETRIEVE INTO, a value partly overwritten where either the write or the old value's bytes are inexact (the old value is dropped), a read spanning the pieces an exact partial write cut a value into, or a RETRIEVE with no matching START. See local site resolution and bounded sweeps.

Example: SPACES is a figurative constant, not a quoted literal, so this MOVE stores no value and the call after it gets no candidate.

MOVE SPACES TO WS-OTHER.
CALL WS-OTHER.               not-a-literal
unmodelled
A statement cobble does not model may have written the field; it counts as a weak write, so the old values stay and this reason joins them.
outside-analysed-set
The program can be entered from callers outside the analysed members, which may hand it other names. See answering every walk once.
not-recorded
The cross-program walk reached a place where the fixpoint recorded no fact. See answering every walk once.

Reasons the per-site resolution on local site resolution gives about the call site itself, two of them shown here: WS-PGMS is a table of names (OCCURS), and WS-PGM holds only spaces.

no-extent
The operand names no storage cobble could lay out, so there is nothing to read.
operand-not-one-exact-extent
The operand could be several places, such as a subscripted WS-PGMS(I), so the site stays unresolved there.
no-program-name
No value reaching the site looks like a program name; the site is resolved to nothing.
no-csd
A RETURN TRANSID or START was analysed without a CSD, so its transaction id cannot be mapped to a program; the site stays unresolved.
transaction-not-in-csd
The transaction id is not listed in the CSD supplied; the site is resolved to nothing, which is wrong if the CSD is merely incomplete.

What goes wrong

  • Under-approximation is the normal case, and the reasons say why. Each code in the taxonomy above names one way the set can be short; any reason at all means "at least these values". Delete the else-arm from the example, as below, and the path that skips the IF reaches CALL WS-PGM with nothing written: the merge in step 4 becomes ({'PROGB␣␣␣'}, {}) ∪ ({}, {uninitialised}). The true set is PROGB plus whatever the storage started as; the analysis can only list the first and flag the second. 
    IF WS-FLAG = 'Y'
    MOVE 'PROGB' TO WS-PGM
END-IF.
CALL WS-PGM.   candidates PROGB
               reasons    uninitialised
  • One candidate is not proof. The call above has a single candidate, but it is not a proven edge, because its reasons are not empty. Row 2 of the table below is that call; row 1 is CALL WS-OTHER in the VALUE 'PROGD' variant, which also has one candidate but no reasons. A walk that stopped early can leave a single value in the set in the same way, while a second was still on its way. That is why a proven edge needs an empty set of reasons, not just one candidate.
    #sitecandidatesreasonsin the graph
    1VALSETV: CALL WS-OTHERPROGDnoneproven: CALL edge
    2no-else variant: CALL WS-PGMPROGBuninitialisedcandidates: CALL_CANDIDATE edge
  • A value is not always a program name. A field can hold spaces on some path. Values that cannot be a program name — nothing left after trimming the spaces, or bytes that are not printable — are dropped from the candidates and recorded separately. A sentinel such as 'NONE' is not dropped: it trims to a name like any other, so it becomes a candidate edge to a program called NONE. The table shows the example with its else-arm changed to each of the two.

    MOVE 'NONE' TO WS-PGM{'NONE␣␣␣␣', 'PROGB␣␣␣'}NONE, PROGBnonetwo CALL_CANDIDATE edges
    In the first row the spaces path leaves one candidate and no reasons, so the edge to PROGB is proven; the spaces stay visible only in the row's dropped list.

In cobble

The fixpoint stage (cobble-dataflow-fixpoint) builds the value sets, applies the budget and records the reasons. It writes each dynamic call site as a targets.jsonl row. These are the two rows it writes for VALSETS; MAIN-PARA/1 and MAIN-PARA/2 are the two CALL statements, and the columns are rows 1 and 2 of the three-way table under the rule.

{"caller": "VALSETS", "node": "MAIN-PARA/1",
 "transfer": "CALL", "expression": "WS-PGM",
 "candidates": ["PROGB", "PROGC"],
 "reasons": [], "dropped": []}
{"caller": "VALSETS", "node": "MAIN-PARA/2",
 "transfer": "CALL", "expression": "WS-OTHER",
 "candidates": [], "reasons": ["uninitialised"],
 "dropped": []}

The graph build (cobble-build) reads those rows and applies the three-way rule. From these two it draws the with value sets box in the graph under the example: two CALL_CANDIDATE edges from the first row, and from the second a CALL edge to a DYNAMIC_TARGET node with id VALSETS.WS-OTHER and reason uninitialised.
