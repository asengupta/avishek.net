Reaching conditions

TL;DRGiven a crash report or a log line pointing at one statement in code nobody on the team wrote, this gives the exact condition on the input that makes that statement run — something you can check against the data that actually came in.

Read first: Visiting a graph

Whether a statement runs is decided by every IF on every path into it: along a path all its guards must hold, where paths merge any one will do, and a branch that never reaches the statement must add nothing. Reachability only says yes or no, and reading guards off by eye across GO TOs misses one or counts a branch that goes elsewhere.

In this page's example, from cobol-rekt's README, an IF WS-NUM1 > 10 jumps to an IF WS-NUM1 = 201 that guards a DISPLAY. The technique slices away the two STOP RUN arms, walks the four statements left in topological order, and gives the DISPLAY the condition AND(C2, C1): WS-NUM1 = 201 and WS-NUM1 > 10. It works on acyclic slices only.

Topological order is explained in Visiting a graph.

The example: a DISPLAY behind two IFs

The page's model of the README program: start A, the IFs as B and C, the DISPLAY as D, a STOP RUN on each arm not taken. The conditions are written C1 and C2:

C1 = WS-NUM1 > 10C2 = WS-NUM1 = 201
flowchart TD
    A -->|always| B["B: IF C1"]
    B -->|C1| C["C: IF C2"]
    B -->|"not C1"| Stop1["STOP RUN"]
    C -->|C2| D["D: DISPLAY"]
    C -->|"not C2"| Stop2["STOP RUN"]

Neither STOP RUN in the graph above leads to D, so the first step throws both away. What is left is the slice from A to D: only the statements and edges on some path from the start to the target. Four statements, three edges:

    C -->|"then: C2"| D

Step by step

The walk visits the slice in topological order, so every statement comes after everything that leads into it, and its predecessors' conditions are already known when it needs them. Each step applies this rule once:

condition(v) = OR, over every incoming edge (u → v):
  AND(that edge's own condition, condition(u))

Diagrams below mark the statement whose condition a step is computing in amber.

Step 4 is the rule box in full: one incoming edge, C → D, whose own condition is C2, ANDed with condition(C), which step 3 left as C1. Each statement in this slice has one way in, so the OR line never has more than one operand here. Step 1 is the OR over no edges at all. AND(C2, C1) means D is reached exactly when both guards hold, and it matches the README output above.

Why each edge carries a condition

Reachability on the first graph says only that D can be reached. To get a condition, every edge is tagged with its own. Leaving an ordinary statement, as at A, control goes the one way it can: always taken, condition TRUE. Leaving an IF, the then-edge carries the IF's condition and the else-edge carries its negation. For the five edges of the first graph:

edgekindits own conditionin the slice?
A → BalwaysTRUEyes
B → CthenC1yes
B → STOP RUNelseNOT C1no
C → DthenC2yes
C → STOP RUNelseNOT C2no

The rule box then reads these off the three rows marked "yes": steps 2, 3 and 4 each took one row's condition and ANDed it with the predecessor's. The two "no" rows would only matter if they led to D; the next example changes the shape so that an else-edge does.

What goes wrong

Each bullet comes with the small case that shows it. The first three are taken from the two walks above.

  • The start statement's own condition reads FALSE, not TRUE. It genuinely does, in the real implementation. A statement with no incoming edge in the whole flowgraph (in practice the program's first statement, the start both walks use) gets the OR over nothing, which the implementation starts from FALSE. Step 1 of both walks shows it:
    statementincoming edgesimplementationcorrect
    AnoneFALSETRUE
    The start is reached unconditionally, so TRUE is what a person would expect. It never surfaces as a wrong final answer for D in either walk, but only because of the next point.
  • AND(lhs, rhs) returns lhs if either side is FALSE, which is correct only when lhs is the FALSE one. Also real. In the implementation's AND, abridged, lhs is the edge's own condition and rhs the predecessor's: 
    if (isFalse(lhs) || isFalse(rhs)) return lhs;
else if (isTrue(lhs)) return rhs;
else if (isTrue(rhs)) return lhs;
return AND(lhs, rhs);
    The three ANDs of the first walk, run through those lines:
    steplhs (edge)rhs (predecessor)returnsboolean AND
    2, at BTRUEFALSETRUEFALSE
    3, at CC1TRUEC1C1
    4, at DC2C1AND(C2, C1)AND(C2, C1)
    In step 2, rhs is the false side: A's wrongly-false condition. The result comes back as the (non-false) lhs, which happens to be the right answer for an always-taken edge out of the start. The two quirks cancel out for every statement directly off the start; nothing here checks that they always will.
  • OR(C1, NOT C1) is never recognised as TRUE. It is a tautology, true for every value C1 could hold:
    C1NOT C1OR(C1, NOT C1)
    TRUEFALSETRUE
    FALSETRUETRUE
    But the rule only simplifies an operand that is already the literal constant true or false, not one that is logically guaranteed to be, so step 4 of the merge walk reports the unsimplified expression. This is a known, stated limitation of the real implementation, not an oversight found by reading between the lines of the code.
  • None of this runs once the slice has a cycle. The rule box needs every predecessor's condition known before a statement needs it, which only a topological order guarantees. Give the slice a loop, as below, and there is none: B has to come before C because of B → C, and after it because of C → B. Building the order throws an exception. 
    flowchart TD
    A -->|always| B
    B -->|always| C["C: IF C1"]
    C -->|"then: C1"| B
    C -->|"else: NOT C1"| D
    linkStyle 1 stroke:#f5b041,stroke-width:3px
    linkStyle 2 stroke:#f5b041,stroke-width:3px
  • Predecessors outside the slice count as TRUE. Even for an acyclic slice, the condition pass reads each statement's incoming edges from the whole flowgraph, not the slice. A predecessor outside the slice has no computed condition and silently defaults to TRUE, understating what is actually required rather than raising an error. Below, P also leads into D but is not reached from A, so the slice from A to D is A, B, D: 
    flowchart TD
    A -->|always| B["B: IF C1"]
    B -->|"then: C1"| D
    B -->|"else: NOT C1"| Stop["STOP RUN"]
    P["P: not reached from A"] -->|always| D
    linkStyle 3 stroke:#f5b041,stroke-width:3px,stroke-dasharray:4

Where this shows up in reverse engineering

  • Triaging a crash report or a log line that points at one statement, like the DISPLAY in the listing: the answer becomes WS-NUM1 = 201 and WS-NUM1 > 10, checkable against the input that triggered it.
  • Security review of legacy code: a dangerous statement in the source may be reachable under no condition a real caller can satisfy; D's row in the table at the top is what to check.
  • The control-side counterpart to a backward data slice: the data version asks "what value reached this read"; this asks the same backward question about control, with the same slice-then-combine shape.

Where this is used

The slice does most of the narrowing: in the example both STOP RUNs were gone before any condition was built.

The same idea, under the same name, drives control-flow structuring in decompilers: Yakdan et al. compute reaching conditions over acyclic regions to turn a recovered flowgraph back into if/else without pattern matching.[1]
