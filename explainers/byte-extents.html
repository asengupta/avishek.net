Byte-extent aliasing

TL;DRIn COBOL, two names can cover the same bytes — group items, REDEFINES, two programs’ copybooks for one commarea. Track names and you miss a value changed under another name; track bytes and you don’t.

Read first: Gen/kill and reaching definitions

Reaching definitions matches a read to the writes of the same name, and lets a new write of that name kill the old ones. Both assume a name owns its storage. But a write to a group never names its children, and a write to one child changes only part of what the group's write left. So the test has to be on byte ranges, and it splits in two — does a write touch a read, and does it wipe out an older write — which can answer differently for the same pair.

In the example below, eight bytes carry four names. Comparing ranges finds that the read of WS-B depends on a MOVE into REC that never names it, and the read of WHOLE on both writes, though neither names WHOLE.

Byte ranges here count from 0 and are half-open: [start, end) includes start and stops just before end, so [0, 4) is bytes 0, 1, 2 and 3, and its length is end − start. What tracking by name misses

The right-hand column of the answer table is what tracking by name gets. It is right for WS-A, because step 2 wrote WS-A by name. It finds nothing for WS-B: step 1 wrote REC, and a group is just the bytes of its children laid end to end, so writing REC wrote WS-B without naming it. It finds nothing for WHOLE either: REDEFINES (analogous to a C union — two names for the same bytes) gives the strip's eight bytes a second name with a different shape, and no statement ever names that one. Two of the three reads would have no source at all. By name, these are the only writes there are:

REC: MAIN-PARA/0WS-A: MAIN-PARA/1WS-B: noneWHOLE: none

Paint the bytes, forget the names

The strips in the walk lay the data out as the compiler does: each field is a start offset and a length in some storage region, the span rows above the cells. A write paints the bytes it covers — step 2 repaints cells 0 to 3 from /0 to /1. A read looks at the bytes it covers and asks which writes painted any of them — the outlined cells in steps 3 to 5. Two fields alias when their ranges overlap, whatever they are called, however they were declared: WHOLE and REC are the same span, and WS-A sits inside both. Every pair of the strip's four names, and the bytes they share:

REC, WHOLE: [0, 8)REC, WS-A: [0, 4)REC, WS-B: [4, 8)WHOLE, WS-A: [0, 4)WHOLE, WS-B: [4, 8)WS-A, WS-B: none

Where this shows up in reverse engineering

Step 5's read through WHOLE is the trap in its smallest form: a write through one REDEFINES view and a read through another look unrelated by name and identical by byte range. A commarea passed between programs is the same picture with the two span rows in two programs: each lays the bytes out with its own copybook, so following a value across the boundary means following its byte range, not either side's field name. The same overlap-versus-cover question comes up in any byte-oriented format — a packed binary buffer, shared memory seen through a foreign-function boundary, a union read as two shapes.

The rule

extent = (region, start, end)
may_alias(a, b) = same region ∧ a.start < b.end ∧ b.start < a.end
exact(w) = w's start and length are known at compile time
must_cover(w, d) = same region ∧ w.start ≤ d.start ∧ d.end ≤ w.end ∧ exact(w)
kill(s) = { d | s's write must_cover d }
definers(read r at s) = { d ∈ in(s) | may_alias(d, r) }

Two different tests, on purpose. A definition is a possible source of a read when it overlaps any byte of it. A definition is certainly gone only when a later write covers every byte it wrote. Anything between — a partial overwrite — leaves it alive. Each line has already run in the walk:

linewhere it ran

definersthe "one definition per write" row in steps 3, 4 and 5

What goes wrong

  • The answer can be loose. At MAIN-PARA/2 (step 3) the strip shows that bytes [0, 4) were last written by MAIN-PARA/1 alone. But the rule keeps one definition per write, and MAIN-PARA/1 covers only half of MAIN-PARA/0's eight bytes, so it cannot kill it. MAIN-PARA/0 still overlaps the read — the top span below — and is reported as a definer although none of its bytes survive there. That is an over-approximation: it never misses a real source, it sometimes names one too many. Getting it exact means splitting a definition into byte ranges whenever something writes part of it. Cobble does that when both the write and the definition are exact: after MAIN-PARA/1 it keeps MAIN-PARA/0 only for REC [4:8], the bottom row of spans, which the read does not touch.

  • Kill only on certainty. A write whose position is not known exactly — a table element with a computed subscript, a field after an OCCURS DEPENDING ON, a reference modification with a run-time start — may alias widely but must cover nothing. Change MAIN-PARA/1 to write four bytes at a run-time position in REC: 
    01  WS-POS  PIC 9.
/1  MOVE 'XXXX' TO REC(WS-POS : 4).
    Its extent is all of REC, but not exact: cobble writes it REC@working_storage[0:8]~, the ~ marking it clamped. It covers nothing, so every read keeps both writes:
    readkill nothing (cobble)if /1 killed /0
    MAIN-PARA/2: WS-A [0:4]MAIN-PARA/0, MAIN-PARA/1MAIN-PARA/1
    MAIN-PARA/3: WS-B [4:8]MAIN-PARA/0, MAIN-PARA/1MAIN-PARA/1

    With WS-POS = 1 the write lands on [0, 4), and WS-B still holds BBBB from MAIN-PARA/0. The right-hand column has lost that source: a wrong answer, not a loose one.
  • A field that cannot be sized has no extent at all, and the analysis cannot place its reads and writes. If WS-A's width were unknown, the strip's ranges after it would be unknown too:

In cobble

Every dataflow stage works on these extents. Each field's extent comes from its declaration alone — level, PIC (which sets the length), usage, OCCURS, REDEFINES. Separate 01 items are laid end to end, as in the example: cobble-extents puts OUT-A at [8:12], straight after REC, and WHOLE back at [0:8]. That is a modelling choice — a real compiler may align or pad between 01 items — and it is safe because distinct 01 items never share bytes unless one REDEFINES another. The two tests are the ones above, whether two extents may overlap and whether one covers all of the other, plus the cut from the first bullet under what goes wrong. A move of a literal has no source field, so cobble names its source LITERAL. Run on this page's program, cobble-dataflow-fixpoint reports these definers, the "cobble" rows of steps 3 to 5 (one row per read, other fields left out):
