Resolving a dynamic call site inside its own program

TL;DRMost dynamic calls take their target from a literal in the same program. The fixpoint's value sets settle those per site, on the spot. Only a site whose name came from outside the program, such as a caller's commarea, needs the cross-program walk.

Read first: Value sets and dynamic calls

PROGA has three dynamic XCTLs. Two take their names from PROGA's own literals, so the walk over PROGA alone finds their targets, with no doubt attached. The third copies its name out of the commarea, so its value set is empty and carries inbound-linkage: a caller decides.

Each site's answer is the value set of its operand where the site runs, found by a forward reaching-definitions walk. Terms are in the COBOL/CICS primer.

Step by step

Each site gets its own walk, over its own operand. The three walks are shown side by side because they visit the same nodes. Each row is the set arriving at that node, which is what the walk reports for a site. Values are shown as stored: PIC X(8) pads 'PROGB' with three spaces, written ␣. The program has no loop, so the worklist visits each node once, in order.

Three forward walks over PROGA (7 steps)

  1. Entry. Each operand starts at what the program holds before any statement runs. WS-FIRST-PGM is covered by a VALUE, so it starts at that literal. The other two have no VALUE: uninitialised. An operand in LINKAGE would start as inbound-linkage.

    operandarriving
    WS-FIRST-PGM{'PROGB␣␣␣'}
    WS-MENU-PGM{} + uninitialised
    WS-NEXT-PGM{} + uninitialised

  2. IF WS-FLAG = 'Y' writes nothing. Both arms start from the same sets.

    operandarriving at each arm
    WS-FIRST-PGM{'PROGB␣␣␣'}
    WS-MENU-PGM{} + uninitialised
    WS-NEXT-PGM{} + uninitialised

  3. Each arm moves a literal into all eight bytes of WS-MENU-PGM. The write is exact, not weak, covers the whole operand, and its values are complete: it replaces. The then arm leaves {'PROGB␣␣␣'}, the else arm {'PROGC␣␣␣'}. The uninitialised doubt is gone on both: the write killed it.

    operandleaving thenleaving else
    WS-FIRST-PGM{'PROGB␣␣␣'}{'PROGB␣␣␣'}
    WS-MENU-PGM{'PROGB␣␣␣'}{'PROGC␣␣␣'}
    WS-NEXT-PGM{} + uninitialised{} + uninitialised

  4. The arms meet at MOVE LK-NEXT TO WS-NEXT-PGM (MAIN-PARA/1), so its arriving set is the union of both. Then the move: it covers all of WS-NEXT-PGM, but it copies rather than storing a literal, so it does not replace. Its source is in LINKAGE, and the write carries inbound-linkage, which is kept.

    operandarrivingleaving
    WS-FIRST-PGM{'PROGB␣␣␣'}{'PROGB␣␣␣'}
    WS-MENU-PGM{'PROGB␣␣␣', 'PROGC␣␣␣'}{'PROGB␣␣␣', 'PROGC␣␣␣'}
    WS-NEXT-PGM{} + uninitialised{} + inbound-linkage

  5. Line 24: XCTL PROGRAM(WS-FIRST-PGM). Its walk arrives with {'PROGB␣␣␣'} and no doubt. Trimmed, that spells PROGB. Resolved to PROGB. The XCTL writes nothing in PROGA and never returns, so it changes none of the three sets.

    line 24 → PROGB

  6. Line 27: XCTL PROGRAM(WS-MENU-PGM). Arrives with {'PROGB␣␣␣', 'PROGC␣␣␣'} and no doubt. Resolved to PROGB and PROGC.

    line 24 → PROGBline 27 → PROGB, PROGC

  7. Line 30: XCTL PROGRAM(WS-NEXT-PGM). Arrives with {} + inbound-linkage. That doubt is not uninitialised, so the site is unresolved: a caller supplies the name. The site goes to the cross-program walk later.

    line 24 → PROGBline 27 → PROGB, PROGCline 30 unresolved: inbound-linkage

Why literals settle it

Steps 3 and 4 of the walk decided line 27. Here is the part of PROGA's graph they covered, with the set of WS-MENU-PGM, line 27's operand, on each edge:

In step 3 each arm overwrites all eight bytes with a literal, so it replaces what arrived, the uninitialised doubt included. In step 4 the arms meet at line 21, so the set is their union; line 21 writes WS-NEXT-PGM, not WS-MENU-PGM. Every value reaching line 27 is a literal this program wrote, so its set is complete.

That is the whole test. If every value reaching a site is a literal this program wrote, the site's answer is complete here. If the name came from linkage, a callee or a file, this program alone cannot see it: the set carries a reason, and the site goes to the cross-program walk.

Where this shows up in reverse engineering

On a large CICS corpus (about 3,800 programs and 19,000 jumps), the dynamic targets came in three shapes, and PROGA has one of each; the line numbers are those of the full listing.

shapein PROGAsiteneeds other programs?
a literal VALUE, never writtenWS-FIRST-PGM ... VALUE 'PROGB' (line 5)line 24no
a MOVE 'LITERAL' on each branchMOVE 'PROGB' / MOVE 'PROGC' TO WS-MENU-PGM (lines 17, 19)line 27no
a name read out of DFHCOMMAREAMOVE LK-NEXT TO WS-NEXT-PGM (line 21)line 30yes

Only the third row, about 5% of the corpus's sites, needs the cross-program walk: a caller put the next program's name in the commarea. That walk is the subject of answering every walk once and bounding walks by crossings.

The rule

initial(o) = inbound-linkage, if o is in LINKAGE
           = the VALUE bytes covering o, if a VALUE covers it
           = uninitialised, otherwise
in(entry) = initial(o);  in(n) = ⋃ out(p) for every predecessor p
out(n) = in(n) after each write w at n:
  w misses o's bytes → unchanged
  w replaces o (exact, covers o, complete values) → w's values, sliced to o
  otherwise → in(n) joined with w's values and reasons
candidates(site) = program names among values(in(site))
complete(site)  ⇔ reasons(in(site)) = ∅

Each line has already run in the walk. initial(o) is step 1: WS-FIRST-PGM starts at its VALUE, the other two at uninitialised. in(n) as a union is step 4, where the arms meet at line 21. The replace line is step 3. Line 21's copy from linkage is why line 30's set carries inbound-linkage.

What goes wrong

Each case is a one-site program ending in XCTL PROGRAM(...), run through cobble-dataflow-fixpoint; the chips are its targets.jsonl row.

  • A path with no write. No ELSE, so on one path nothing writes the operand. The literal is found, and the gap is marked: 
               IF WS-FLAG = 'Y'
               MOVE 'PROGB' TO WS-PGM
           END-IF.
    candidates: PROGBreasons: uninitialised
  • Conditions are not evaluated. A literal on a branch that never runs still counts. Nothing writes WS-NEVER, yet PROGC is a candidate. Loose, not wrong: 
           01  WS-PGM               PIC X(8) VALUE 'PROGB'.
       01  WS-NEVER             PIC X VALUE 'N'.
       ...
           IF WS-NEVER = 'Y'
               MOVE 'PROGC' TO WS-PGM
           END-IF.
    candidates: PROGB, PROGCreasons: none
  • The walk starts at the program's entry. A CALLed batch subprogram keeps its working storage between calls. Below, the site runs before the MOVE, so the walk sees only uninitialised; on a second call, WS-PGM already holds 'PROGB' from the first. The reason says the set may be short, but the candidate is missed: 
               CALL WS-PGM USING DFHCOMMAREA.
           MOVE 'PROGB' TO WS-PGM.
           GOBACK.
    candidates: nonereasons: uninitialised

Two cases that look hard are not. A copy of a literal through another field (MOVE 'PROGB' TO WS-OTHER, MOVE WS-OTHER TO WS-PGM) gives PROGB with no reasons, because the value set travels with the bytes. A table of names read with a computed subscript (XCTL PROGRAM(WS-PGMS(WS-I)) over 'PROGB' and 'PROGC') gives both, with no reasons.

In cobble

The resolution is part of cobble-dataflow-fixpoint: every dynamic site's operand gets its value set where the site runs, and the run writes one targets.jsonl row per site. For PROGA:

{"caller": "PROGA", "node": "MAIN-PARA/2.when.0.0", "transfer": "CICS_XCTL",
 "expression": "WS-FIRST-PGM", "candidates": ["PROGB"], "reasons": []}
{"caller": "PROGA", "node": "MAIN-PARA/2.when.1.0", "transfer": "CICS_XCTL",
 "expression": "WS-MENU-PGM", "candidates": ["PROGB", "PROGC"], "reasons": []}
{"caller": "PROGA", "node": "MAIN-PARA/2.when.2.0", "transfer": "CICS_XCTL",
 "expression": "WS-NEXT-PGM", "candidates": [], "reasons": ["inbound-linkage"]}

The commands, with the bridge environment sourced and a corpus config listing PROGA:

cobble-parse-corpus --config corpus.toml
cobble-extents --asg-dir asg --out extents.jsonl
cobble-dataflow-fixpoint --asg-dir asg --extents extents.jsonl --out-dir fixpoint --all

cobble-dataflow-combine then takes every site whose reasons say a caller or callee decides, and walks across programs for it. Next: sweeps.
