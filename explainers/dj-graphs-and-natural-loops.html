DJ graphs and natural loop bodies

Read first: Reducibility and loop detection, Dominance and reachability

Reducibility answers yes or no, and roughly where. It does not say which statements belong to which loop when there is more than one, nested or side by side. One structure — the DJ graph — answers that, by processing a method's loops from the inside out, one dominator level at a time.

Where this shows up in reverse engineering

Knowing a method is reducible is not the same as knowing which statements belong to which loop — and once there is more than one loop, nested or side by side, that distinction is exactly what the next tool in the pipeline needs.

  • Automatic narration of an unfamiliar program needs the exact loop body before it can say anything more specific than "there is a loop somewhere in here": telling an outer loop's statements apart from an inner one's is what lets a narration describe each one correctly instead of describing the inner loop's statements as if they belonged to the outer one, or vice versa.
  • A decompiler nesting loops correctly in its emitted source has the identical requirement: get the body boundary wrong by one statement and the generated code either runs an extra statement inside the wrong loop or runs one outside a loop it should be inside.
  • Why bottom-up, specifically: resolving the innermost loop first and collapsing it before asking about the loop around it is what keeps the outer loop's own analysis from ever needing to know the inner loop's statements existed — the only way this scales to a method with several loops at several nesting depths without re-deriving the same boundary information at every level.

The problem

Reducibility and loop detection settles whether a flowgraph is well-behaved at all, and the strongly-connected-components method there points at roughly where the trouble is. Neither one hands back the thing a structuring tool actually needs: for this specific loop, the exact set of statements inside it — and when one loop sits inside another, the inner one's statements need to be told apart from the outer one's before either body means anything.

The structure below, the DJ graph, was introduced by Sreedhar and Gao for a different problem — placing φ-nodes in static single assignment form.[1] Sreedhar, Gao and Lee then reused it for this one: identifying every loop's exact body, nested ones included, in one bottom-up pass.[2] The dominator-tree reducibility test on the reducibility page is a piece of that second paper too. The rest of it, covered here: process a method's dominator tree from its deepest level up, and at every level, either collapse a loop that was just found into a single stand-in statement, or discover that no single statement can be called that level's loop header at all.

The DJ graph

A DJ graph takes a method's control-flow graph and splits its edges into three kinds, each telling you something different:

  • Dominator-tree edges ("D-edges") — unchanged from the dominator tree. These are the edges that say "to reach B, execution must first pass through A." They give each statement a depth: how many dominator-tree edges separate it from the method's entry point, which sits at depth 0.
  • Back-join edges ("J-edges, backward") — edges from the original flowgraph where the target dominates the source. These are loop-closing edges: control flows from inside a loop back up to the loop's header. The target of a back-join edge is always a loop header.
  • Cross-join edges ("J-edges, sideways") — the remaining flowgraph edges, where the target does not dominate the source. Most are harmless: every if/else merge produces them — in dominance and reachability's diamond, B3 → D and C → D are both cross-join, and that graph is perfectly reducible. A cross-join edge signals an irreducible region only when it is also a DFS back edge — when it closes a cycle without its target dominating its source.

"Back edge" has two senses, and this page needs both. In the DFS sense, it is an edge a depth-first walk finds going to a statement still on its current path. In the dominator sense, it is an edge whose target dominates its source — a back-join edge. On a reducible graph the two pick out exactly the same edges; a DFS back edge that is cross-join instead is precisely where they disagree, and precisely an irreducible region.

The classification rule is the same one reducibility and loop detection's third method already uses. What is new is doing it once over the whole method, annotating each statement with its dominator-tree depth, so that a bottom-up pass knows which level to process next.

Why depth matters. A loop can only be nested inside loops whose headers are ancestors of its own header in the dominator tree — so an enclosing loop's header is always shallower than the loops it contains. (Two headers on different branches of the tree are unrelated, whatever their depths.) Processing from deepest to shallowest therefore means the innermost loops get resolved first, before the outer loops that contain them need to know their boundaries.

A small nested example — an inner loop (B, B1, B2) sitting inside an outer one (A through D):

    Entry["Entry · d0"] --> A["A · d1"]
    A --> B["B · d2"]
    B --> B1["B1 · d3"]
    B1 --> B2["B2 · d4"]

    D --> Exit["Exit · d7"]

Every solid edge above is already a dominator-tree edge — this particular shape happens to be a straight chain of immediate dominators. Classifying the two dashed edges the usual way: does B dominate B2? Yes — back-join. Does A dominate D? Yes — back-join. Both climb to the header of the loop they belong to. This graph happens to have no cross-join edges at all; it is fully reducible, nested two deep. (One with cross-join edges could be just as reducible, as long as none of them is also a DFS back edge.)

The intuition

Think of it this way. You have a method with several loops, some nested inside others. You want to know the exact body of each loop — which statements belong to it and which don't. The strategy is to start with the smallest, innermost loops and work outward.

Why inside-out? If you tried to identify the outer loop first, you'd have to figure out which statements are "really" in the outer loop versus which ones only appear to be because they're inside an inner loop that happens to be inside it. That's a mess — you'd end up re-analyzing the inner loop's boundaries every time you look at the outer one. Instead: find the inner loop first, collapse it into a single point, and then the outer loop has one fewer thing to worry about.

Collapsing the nested loop, bottom-up

The algorithm walks the dominator tree's levels from deepest to shallowest. At each level it first asks one question: does a back-join edge land on a statement at this level? (A second question, for irreducible regions, comes in the next section.)

  • Yes — that statement is a loop header. Find the loop's body by walking backward from the back edge's source, collecting every statement along the way, and stopping when you reach the header. This is the same bounded backward walk from dominance and reachability's loop section; it always stops at the header because the header dominates every statement in the body, so every backward path from the body must reach it. Then collapse the entire body into the header: remove the body's statements from the graph, and redirect any edge that left the body to start at the header instead.
  • No — no natural loop at this level. Move on to the next shallower level. (If a cross-join edge that is also a DFS back edge lands at this level, the level holds an irreducible region — handled in the next section, and possible whether or not the level also had a natural loop. Plain cross-join edges, like an if/else merge, change nothing.)

Why collapsing works. After the collapse, the header stands in for everything the loop contained. An outer loop at a shallower level, when its own turn comes, sees the collapsed header as a single ordinary statement. It never needs to re-examine the inner loop's body — the inner loop's boundary is already resolved and locked in, so no statement is walked again by every loop that encloses it.

Why redirecting edges is safe. Any edge that left the body (like B2 → C in the example below) is redirected to start at the header (B → C). This is correct because the header is the only way into the loop — so from the rest of the program's perspective, the loop's output is indistinguishable from its header's output. The edge keeps its original classification (back-join, cross-join, or dominator) so that levels above can still use it correctly.

Two natural loops, correctly told apart, in one bottom-up pass — the inner one collapsed before the outer one's own back edge was even inspected, so the outer loop's walk never had to know B1 or B2 existed. The redirected edges keep their original type for exactly this reason: a back-join or cross-join edge that happens to skip past this loop's own header, straight to an outer ancestor, carries that fact up to whichever shallower level needs it next — the same one-level-at-a-time climb eliminating GOTOs uses for a jump nested several scopes deep.

When a level is irreducible instead

The algorithm above relies on finding a back-join edge to identify a loop header. A cycle that closes through a cross-join edge instead — a cross-join edge that is also a DFS back edge, landing on a statement at this level — is the hallmark of an irreducible region: a cycle with more than one entry point, so there is no single statement that dominates the rest. No bounded backward walk can find the body, because there is no header to walk back to. (Cross-join edges that are not DFS back edges close no cycle and are no signal at all.) A level can hold both kinds: its natural loops are collapsed by the walk first, then whatever irreducible region remains is handled as below.

When this happens, the algorithm falls back to a stronger tool: it takes every statement at this dominator depth (or deeper) that is still in the graph and runs a strongly connected components analysis. Any component with more than one member is an irreducible region. It gets collapsed the same way a natural loop does — merged into a single stand-in statement — so that levels above can continue without knowing there was anything unusual.

Back on the two-entry cycle from the reducibility page — the smallest irreducible shape there is:

flowchart TD
    Entry --> A
    Entry --> B
    A -->|cross-join| B
    B -->|cross-join| A

A DFS over this DJ graph from Entry, visiting A before B, finds exactly one back edge: B → A, already classified cross-join. A → B is cross-join too, but the DFS took it as an ordinary forward step, so on its own it would mean nothing; B → A being both cross-join and a DFS back edge is the signal to try the quicker check.

What differs is how the body was found: a bounded backward walk from one edge for a reducible loop, a full strongly-connected-components pass for an irreducible region, because an irreducible region has no single back edge whose header could have been walked back from in the first place.

What goes wrong

Two limitations to be aware of, both consequences of the design rather than bugs:

  • An irreducible region's recorded "header" is an artifact of visitation order, not a property of the region. A natural loop has a true header — the one statement that dominates every node in its body. An irreducible region, by definition, has no such statement. The tool described here still picks one statement to serve as the stand-in after collapsing — its own convention, not the paper's — and uses whichever statement the DFS happened to identify as the target of its back edge. Run the DFS over the same two-entry cycle visiting B before A instead, and the back edge found is A → B, not B → A — the identical region collapses to a different stand-in statement depending on which child of Entry happened to be visited first:
    Entry's children visitedDFS back edge foundrecorded header
    A, then BB → AA
    B, then AA → BB
    That is not a bug so much as an honest consequence of the question itself: an irreducible region, by definition, has no single header, so any one statement the algorithm names as "the" header for it is already a necessary approximation — just not a stable one across runs.
  • A collapsed body is reported in terms of whatever was already collapsed underneath it, not fully expanded back out. Because the algorithm works bottom-up, by the time an outer loop is processed, its inner loops have already been collapsed into single stand-in statements. The outer loop's reported body includes these stand-ins, not the original statements they absorbed. This is a feature for the algorithm's own operation (it's what keeps an outer loop from re-walking its inner loops' statements), but it means that if you need the full list of original statements, you must expand the stand-ins by looking up what each one absorbed. The outer loop above is recorded as {A, B, C, D} — B there means the single stand-in statement, not the three original statements it absorbed:
    headerreported bodyoriginal statements, fully expanded
    B{B, B1, B2}{B, B1, B2} — not nested, nothing to expand
    A{A, B, C, D}{A, B, B1, B2, C, D} once B's own body is substituted back in
    Reading a reported body as the complete statement list, for a loop that turns out to have another one nested inside it, undercounts by exactly the inner loop's size.

Putting it together

The full algorithm, in plain English:

  1. Build the dominator tree. Record each statement's depth.
  2. Classify every edge that is not a dominator-tree edge: if the target dominates the source, it's a back-join edge (a loop closing); otherwise it's a cross-join edge (a sideways jump). Run a DFS and mark every cross-join edge that is also a DFS back edge.
  3. Starting from the deepest level and working up:
    • If a back-join edge lands on a statement at this level — it's a loop header. Walk backward from the edge's source to find the body. Collapse the body into the header.
    • If a marked cross-join edge — one that is also a DFS back edge — lands on a statement at this level, the level is irreducible. Once any natural loops at this level are collapsed, find the strongly connected components among the statements at this depth or deeper, and collapse each one with more than one member.
    • If neither — nothing interesting at this level (unmarked cross-join edges, like if/else merges, don't count), move up.
  4. When you reach the root, every loop's body has been identified and collapsed.

On top of building the dominator tree and walking every edge to classify it, the pass visits each level once, does one backward walk per loop found, and one strongly connected component search per irreducible level. For reducible graphs, Sreedhar, Gao and Lee bound the whole thing at near-linear time by doing the collapsing with a union-find structure.[2] Irreducible levels cost more: each search covers every statement at that depth or deeper, so the same statements can be searched again at several levels. On a typical COBOL program — where irreducible regions are rare and loops rarely nest more than two or three deep — this finishes almost instantly.

Where this is used

The three edge types this page builds — dominator, back-join, cross-join — are not thrown away once reducibility and loop bodies are known. They serve at least two purposes downstream:

  • A transpiler emitting structured code switches on exactly these three edge classes when deciding how to represent each edge: a back-join edge becomes a loop, a forward dominator edge becomes straight-line code or an IF, and a cross-join edge that is also a DFS back edge (if any) marks the irreducible region that needs the more expensive restructuring from eliminating GOTOs. The classification done here survives into code generation, not just into an analysis report.
  • A narration or documentation tool uses the loop bodies to scope its descriptions: "this loop iterates over records" is only meaningful if the tool knows exactly which statements are inside the loop and which are after it. Without the DJ graph's output, the best it can do is "there is a loop somewhere near these statements."
