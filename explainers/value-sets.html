Where this shows up in reverse engineering

Any call graph for a program with dynamic dispatch has this hole in it until something fills it in — the question is always the same: what values can actually reach the thing deciding where to go next.

  • A menu, a router, a transaction dispatcher — any program whose next call is chosen by a field's runtime value rather than written as a literal — is invisible to a call graph built by reading CALL statements alone. The value-set technique on this page is what turns that into a graph with real edges instead of a gap at every dispatch point.
  • The same question, on the Java side, over a different kind of value: a backward data-dependency walk that crosses method boundaries can resolve a literal that reaches a dynamically-dispatched call's argument several call frames up — the identical "what value could this hold" question, answered by walking data flow backward instead of forward.
  • Virtual dispatch resolution is a value-set problem one level up: "every concrete class an interface call's receiver could actually be at runtime" is the same kind of set, just over types instead of string literals — a call graph builder resolving polymorphic calls is running this page's technique on a different domain.

The problem

CALL 'PROGB' names its target in the source; a call graph can draw that edge by reading it. CALL WS-PGM calls whatever program name is in WS-PGM when the statement runs. Leave those edges out and the call graph has holes exactly where a program dispatches on data — menus, routers, transaction handlers. Guess and it draws edges that do not exist.

The intuition

For every field, carry the set of byte values it may hold at each statement. A MOVE of a literal sets it to exactly that value. A MOVE from another field copies that field's set. Where paths meet, take the union. At a CALL through a field, the field's set is the list of programs that call could reach.

The set can be incomplete: the value may come from a file, from a caller, or from nowhere the analysis can see. So each set also carries reasons it may be missing values. An empty set of reasons means "these and no others"; any reason means "at least these".

The example

Two branches put different program names into WS-PGM before calling through it. A second call goes through WS-OTHER, which nothing assigns.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. VALSETS.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-FLAG              PIC X.
       01  WS-PGM               PIC X(8).
       01  WS-OTHER             PIC X(8).
       PROCEDURE DIVISION.
       MAIN-PARA.
           IF WS-FLAG = 'Y'
               MOVE 'PROGB' TO WS-PGM
           ELSE
               MOVE 'PROGC' TO WS-PGM
           END-IF.
           CALL WS-PGM.
           CALL WS-OTHER.
           STOP RUN.

The rule

value set = (values, reasons)
entry : f := ({f's VALUE bytes}, {}) if f has a VALUE clause, else ({}, {uninitialised})
MOVE literal TO f : f := ({literal padded or truncated to f}, {})
MOVE g TO f : f := g's set
merge : (values₁ ∪ values₂, reasons₁ ∪ reasons₂); if more than 32 values, keep the first 32 in sorted order and add over-budget
call through f : candidates = trimmed values of f, reasons = f's reasons

The entry line plays the part of the teaching-only start definition on the fixpoints page (cobble itself has no such definition): a VALUE clause supplies the field's starting value, and without one the starting value is unknown. The two MOVE lines gloss over size: when source and target differ in length, an alphanumeric MOVE pads the target with spaces or cuts the value off on the right, so read them as applying that to each value in the set.

A call site then becomes one of three things in the graph:

  • Proven — exactly one candidate and no reasons. An ordinary call edge, as if the name were written in the source.
  • Candidates — any other site with at least one candidate. One edge per candidate, marked as possible rather than certain.
  • Unresolved — no candidates. A single dynamic-target node carrying the expression and the reasons, so the hole is visible rather than silent.

Reasons taxonomy

Each reason explains why a value set may be incomplete — why the true set of values could be larger than what the analysis found.

uninitialised
Some path reaches this point without an exact write to the field, and no WORKING-STORAGE VALUE that cobble can image (text, figurative, or unsigned zoned) covers it. On that path its value is whatever the storage started as. (Introduced here.)
over-budget
More than 32 values reached the field. The first 32 in sorted order are kept; the rest are dropped. The field may have that many possible values — some may come from paths that never actually run — but the analysis cannot carry all of them. (Introduced here.)
incomplete-walk
The fixpoint stopped before settling because it ran out of its sweep budget — the cap on how many passes over the program it may make. Values that would have arrived on later passes are missing. See bounded sweeps.
hop-limit
The cross-program walk — following a field's bytes backwards from one program into the programs that handed them over (answering every walk once) — was cut after a fixed number of program crossings. Programs beyond that depth were never visited. See bounding walks by crossings.
readback-skipped
The cross-program walk was told not to follow bytes a called program writes back to its caller, so names a callee puts in the commarea are missing. See bounding walks by crossings.

The value comes from somewhere a single program's walk cannot follow:

inbound-linkage
The bytes are in LINKAGE: a caller handed them in. Also used when a cross-program walk goes round a cycle of programs and finds nothing. See local site resolution and answering every walk once.
from-callee
A LINK or CALL BY REFERENCE handed the field to another program, which may have written it. See local site resolution.
from-file
A READ or a CICS file command put the value there. See local site resolution.
not-a-literal
The value is not a quoted literal, so the analysis does not evaluate it: arithmetic (ADD through COMPUTE), STRING, INITIALIZE, a numeric or figurative MOVE such as MOVE 0 or MOVE SPACES, a non-file CICS receiver such as RETRIEVE INTO, a value partly overwritten by an inexact write, or a RETRIEVE with no matching START. See local site resolution and bounded sweeps.
unmodelled
A statement cobble does not model may have written the field; it counts as a weak write, so the old values stay and this reason joins them.
outside-analysed-set
The program can be entered from callers outside the analysed members, which may hand it other names. See answering every walk once.
not-recorded
The cross-program walk reached a place where the fixpoint recorded no fact. See answering every walk once.

Reasons the per-site resolution on local site resolution gives about the call site itself:

no-extent
The operand names no storage cobble could lay out, so there is nothing to read.
operand-not-one-exact-extent
The operand could be several places, such as a subscripted WS-PGMS(I), so the site stays unresolved there.
no-program-name
No value reaching the site looks like a program name; the site is resolved to nothing.
no-csd
A RETURN TRANSID or START was analysed without a CSD, so its transaction id cannot be mapped to a program; the site stays unresolved.
transaction-not-in-csd
The transaction id is not listed in the CSD supplied; the site is resolved to nothing, which is wrong if the CSD is merely incomplete.

What goes wrong

  • Under-approximation is the normal case, and the reasons say why. Each code in the taxonomy above names one way the set can be short; any reason at all means "at least these values".
  • One candidate is not proof. A walk that stopped early can leave a single value in the set while a second was still on its way. That is why a proven edge needs an empty set of reasons, not just one candidate.
  • A value is not always a program name. A field can hold spaces or a sentinel like 'NONE' on some path. Values that cannot be a program name are dropped from the candidates and recorded separately.

In cobble

The fixpoint stage (cobble-dataflow-fixpoint) builds the value sets, applies the budget and records the reasons. It writes each dynamic call site as a targets.jsonl row. The graph build (cobble-build) reads those rows and applies the three-way rule.
